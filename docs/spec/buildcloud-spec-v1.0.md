## 1. 项目概述

### 1.1 一句话定位

面向建筑施工企业的**工程项目管理平台**：微服务架构，覆盖项目立项、合同资金、材料库存与集中申领（高并发主战场）、多级审批、异步报表，并内置基于 RAG 的企业制度/施工规范知识库问答。

### 1.2 背景叙事（面试自我介绍的底稿）

> 第一段实习在建筑公司技术部门全栈维护工程项目管理平台，接触立项、合同、材料、审批等业务；实习期间发现单体架构在材料集中申领、大报表导出等场景存在性能与可用性瓶颈。因此业余时间参考开源企业级微服务基座（系统管理/权限/工作流等通用能力），按微服务架构重新实现这套业务域，并对高并发申领链路做专项设计与压测验证；同时结合对 AI 应用开发的兴趣，实现 RAG 制度知识库。最终完成**云服务器部署上线**并对外演示。

简历对外表述口径（诚信红线）：**"基于开源微服务基座做二次开发，通用能力（用户/权限/工作流引擎）来自基座，六个业务域、高并发链路、AI 模块、部署上线为自己设计与实现"**。被直接问"是不是芋道改的"时大方承认基座来源——与真实公司里基于内部平台二次开发的工作模式一致。

### 1.3 目标（Goals）

1. 完成六域业务闭环，可全流程演示（立项→合同→申领→审批→出库→报表→AI 问答）；
2. 产出**压测报告**：申领链路 V1（同步扣减）vs V2（Redis 预扣 + MQ 异步）的量化对比，0 超卖可验证；
3. 覆盖大厂 Java 后端面试核心考点：缓存、MQ、分库分表、分布式事务、微服务治理、幂等/一致性；
4. AI 模块覆盖 AI 应用开发岗考点：RAG 全链路、SSE 流式、会话记忆、引用溯源、Token 限流；
5. 完成云服务器部署上线，沉淀「部署上线」经历与运维手册（D20）。

### 1.4 非目标（Non-Goals，明确不做）

- 不做支付、商城、会员、公众号、CRM/ERP/WMS 等基座自带业务模块（裁剪掉）；
- 不做移动端 / 小程序 / uni-app 前端（管理端 Vue3 仅裁剪适配，不做深度前端定制）；
- 不做多租户商业运营（仅演示单租户 + 部门数据权限，多租户能力沿用基座但不展开）；
- 不重造权限体系（RBAC / 登录 / 数据权限直接用基座）；
- 不接真实外部系统（短信、支付沙箱、真实企业微信等均不接）；
- 不追求生产级安全合规（密钥管理按 demo 级，做脱敏与基本防护即可——但**公开仓库零密钥泄漏是硬约束**，见 §4.3）。

### 1.5 成功标准（验收总纲）

| 维度 | 标准 |
| --- | --- |
| 功能 | 六域端到端演示脚本跑通（含一条完整审批流） |
| 性能 | 压测报告出具：V2 申领接口 QPS ≥ V1 × 5，P99 < 200ms（目标值，实测以报告为准），**0 超卖断言通过** |
| 质量 | 核心链路（预扣/消费/回滚/对账）有单元测试与集成测试 |
| 文档 | README + 架构图 + ER 图 + 压测报告 + 面试 Q&A 弹药库 + 一键启动手册 + **部署上线手册** |
| 部署 | 云服务器（约 2C4G）精简编排部署成功，公网可访问演示 |
| 可讲性 | 每个简历亮点能扛住"为什么这么做 / 替代方案 / 线上出问题怎么办"三层追问 |

## 2. 系统边界

### 2.1 组织与角色模型

- 租户 = 建筑公司（演示一家）；部门 = 职能部门与项目部（树形，数据权限挂部门）；
- 角色：平台超管、公司管理员、项目经理、材料员、财务、审批人（部门经理/总经理）。

### 2.2 核心用例（按域，一期全部实现）

| 域 | 用例 |
| --- | --- |
| 项目域 | 立项（走审批）、项目台账、WBS 里程碑、项目成员（数据权限）、暂停/复工/竣工 |
| 合同域 | 合同登记（收入/支出）、收付款计划、进度款申请（走审批）、变更签证、合同台账对账 |
| 材料域 | 物料目录/供应商维护、入库、**集中申领（高并发链路）**、申领审批、出库、退料、库存流水与对账 |
| 审批域 | 基于基座 Flowable：立项审批、进度款审批、材料申领审批（会签/驳回/超时自动处理） |
| 报表域 | 项目成本汇总、材料消耗汇总、收付款汇总；**大数据量异步导出**（分片任务 + 流式写 + 通知） |
| AI 域 | 制度/规范文档上传与向量化、知识库问答（RAG + SSE + 引用溯源）、会话管理 |

### 2.3 压测场景边界

高并发主战场**只取一个**：材料集中申领（场景设定：月底/开工高峰，多工地同时申领同一物料，瞬时 1000 并发打同一库存记录）。其余接口按常规缓存优化即可，不铺开。压测环境固定为**本机**（D18），云服务器只做演示部署。

## 4. 基座裁剪方案（改动清单）

### 4.1 基座获取与仓库落地

- 源：https://github.com/YunaiV/yudao-cloud 的 **master-jdk17 分支**（Gitee 主仓库：zhijiantianya/yudao-cloud）；
- 方式：clone 后拷入**本仓库** https://github.com/zzzc411/buildcloud （公开，D21），保留 MIT 协议文件；本地开发位置 `D:\project\Engineering Management Platform`（D20/D21）；

### 4.2 模块处置清单（对照 yudao-cloud 根 pom 的 modules）

| 处置 | 模块 | 说明 |
| --- | --- | --- |
| **保留** | yudao-dependencies / yudao-framework / yudao-gateway / yudao-server / yudao-module-system / yudao-module-infra / yudao-module-bpm | 依赖管理、框架 starters、网关、系统、基础设施、工作流 |

### 4.3 连带改动点（删模块不止是删目录）

1. 根 pom：modules 列表增删；
2. Nacos 配置：清理被删模块的配置（以仓库内配置目录 + quick-start 说明为准）；
3. SQL：`sql/` 目录只保留 system/infra/bpm 所需脚本 + 自建 `bc_*` 业务表脚本；
4. 网关路由：删除指向被删模块的路由，新增 4 个 buildcloud 服务路由；
5. system 菜单/角色/字典初始化 SQL：删除无关菜单，插入项目管理平台的菜单树（项目/合同/材料/报表/AI 五大菜单组）；
6. 前端 yudao-ui-admin-vue3：删除无关页面路由与菜单，保留登录/用户/权限/工作流/基础设施页面，新增 buildcloud 各域页面（由代码生成器产出后手改）；
7. README/LICENSE：重写 README 为筑云项目说明，保留并注明基座来源与 MIT 协议；
8. **敏感信息治理（公开仓库硬约束，D19/D21）**：所有 `application-*.yaml` / Nacos 配置中的密钥（LLM API Key、数据库密码、Redis 密码、云服务器信息）一律模板化——仓库内只提交 `*-template.yaml` 或 `${env:XXX}` 占位符，真实值走本地未跟踪文件 / 环境变量 / Nacos 本地实例；提交前 grep 扫描。

## 5. 业务域设计

> 所有业务表沿用基座 BaseDO 规范：`tenant_id / creator / create_time / updater / update_time / deleted`。错误码、分页、统一响应、Swagger、日志规范全部沿用基座约定（§7）。

### 5.1 项目域 + 合同资金域（buildcloud-module-project，D17 合并）

两个业务子域在同一模块内**分包隔离**（`com.buildcloud.project.*` / `com.buildcloud.contract.*`），表、错误码段、菜单各自独立——保持领域清晰，将来拆分服务时只动部署不动设计。

**项目子域**：
- 实体：`bc_project`（项目：编号/名称/类型/状态/省市/建设单位/合同额/计划与实际开竣工/项目经理/所属部门）、`bc_project_milestone`（里程碑：名称/计划与实际日期/权重/状态）、`bc_project_member`（项目成员：项目/用户/项目内角色）；
- 用例：立项（提交→Flowable 立项审批→通过后状态"在建"）、台账查询（分页+多条件）、里程碑维护、成员维护、暂停/复工/竣工（状态机）；
- 项目状态机：`筹备 → 在建 ⇄ 停工 → 竣工`；
- 数据权限：按部门（基座数据权限）+ 项目成员白名单双维度控制"谁能看哪些项目"。

**合同子域**：
- 实体：`bc_contract`（合同：编号/名称/关联项目/收入或支出/金额/签订日期/状态）、`bc_contract_payment_plan`（收付款计划：期次/计划金额/计划日期/状态）、`bc_contract_payment_record`（实际收付：金额/日期/关联审批单）、`bc_contract_change`（变更签证：类型/增减金额/原因/关联审批）；
- 用例：合同登记、计划编制、进度款申请（走审批，通过后生成 payment_record 并回写合同累计收付）、变更登记、台账对账（计划 vs 实际差异）；
- 合同状态机：`草稿 → 审批中 → 履行中 → 已结算`，旁路 `已作废`。

### 5.2 材料域（buildcloud-module-material）— 高并发主战场

- 实体：`bc_material_category`（树形目录）、`bc_material`（物料：编码/名称/规格/单位/目录）、`bc_supplier`（供应商）、`bc_material_stock`（库存：项目+物料 唯一，`available_qty / locked_qty / version` 乐观锁）、`bc_requisition`（申领单：`req_no` 全局唯一/项目/申请人/状态/超时时间）、`bc_requisition_item`（明细：申领单/物料/数量）、`bc_stock_log`（库存流水：`biz_type` 入库/申领/退回/冲正、`biz_no`、数量±、变动后余额，**分库分表主表**）；
- 申领单状态机（核心）：

```
草稿 ──提交──▶ 已提交(已预扣) ──审批通过──▶ 已扣减 ──出库──▶ 已出库 ──核销──▶ 已完成
                    │                                              │
                    ├──审批驳回──▶ 已取消(回滚预扣+冲正流水)          └──退料──▶ 部分回退
                    └──超时未审完(延迟消息)──▶ 已关闭(回滚预扣+冲正流水)
```

- 用例：目录/供应商维护、入库（写 stock + stock_log）、**集中申领**（详见 §6.1）、申领审批（Flowable）、出库、退料、流水查询、库存对账（Job）。

### 5.3 审批域（基座 bpm 集成，不新增服务）

- 三条流程定义：`project-approve`（立项）、`payment-approve`（进度款）、`requisition-approve`（材料申领，含会签示例）；
- 集成方式沿用基座模式（参照其 OA 请假示例）：业务单据 ↔ 流程实例的发起/回调/驳回/撤回；审批结果通过 MQ 广播给业务方与站内信；
- 演示特性至少覆盖：会签、驳回至发起人、超时自动处理（配置超时规则）。

### 5.4 报表域（buildcloud-module-report）

- 实体：`bc_report_job`（导出任务：类型/查询参数/状态/文件 URL/失败原因）；
- 用例：项目成本汇总、材料消耗汇总、收付款汇总（查询接口 + 看板聚合）；**异步导出**：请求→建任务（WAITING）→XXL-Job 分片广播按项目分片查询→EasyExcel 流式写→上传 MinIO→站内信通知下载→DONE；失败重试与幂等（任务状态机 + 分片断点）。

### 5.5 AI 域（buildcloud-module-ai）

- 实体：`bc_ai_doc`（文档：名称/文件/解析状态/分块数）、`bc_ai_chat_session`、`bc_ai_chat_message`（含引用的 chunk id 列表）；向量与分块存 PostgreSQL + pgvector（`bc_ai_chunk(id, doc_id, content, embedding vector)`）；
- 用例：上传制度/规范文档（PDF/Word）→Tika 解析→按 512 token 滑窗分块（64 重叠）→embedding 入库；问答：问题→(可选改写)→向量 topK + 关键词混合检索→上下文组装（带来源）→LLM SSE 流式输出→会话记忆（Redis，最近 N 轮）→引用溯源展示；
- **LLM 接入（D19）**：统一走 OpenAI 兼容协议，主 DeepSeek、备通义等；`provider / model / base-url / api-key / 超时 / 重试` 全部为 Nacos 动态配置，支持运行期切换与故障切换；本地开发用环境变量或本地配置文件注入 Key；预算约 ¥50，代码内置 Token 用量统计与限额熔断；
- 工程点：Token 限流（Redis 漏桶/用户）、Prompt 模板版本管理、多模型故障切换、敏感信息先脱敏再送模型、拒答阈值（检索相关度低于阈值时明确拒答，防幻觉）。

## 6. 核心技术专项设计（简历弹药）

### 6.1 材料集中申领高并发链路（V1 → V2 对照）

**V1（基线，W4 实现）**：提交申领 → 同一事务内 `SELECT ... FOR UPDATE` 锁库存行 → 校验并扣减 → 写申领单与流水。问题：行锁串行化，热点库存记录成为瓶颈，吞吐随并发骤降——**这是压测对照组，不是要保留的方案**。

**V2（目标架构，W5 实现）**：

```
提交申领
  ① 网关 Sentinel 限流（接口级 + 热点参数 materialId）
  ② 快速校验：布隆过滤器（Redisson BF，material id 存在性）→ 物料目录缓存（Caffeine+Redis 两级）
  ③ Redis Lua 原子预扣：KEY pm:stock:{projectId}:{materialId}
     脚本语义：available >= qty ? decr + 记录预扣明细(reqNo→hash) : 返回失败
     失败 → 友好降级（"库存不足/排队中"），不打 DB
  ④ 发 RocketMQ 事务消息（half 消息）
        └ 本地事务：创建申领单(已提交) + 写 pending 扣减流水
        └ commit → 消费者：DB 真实库存扣减（乐观锁 version）
                    + stock_log 落库（分片表）+ 状态→已扣减
        └ 本地事务失败 → rollback，MQ 丢弃 half 消息
  ⑤ 审批（Flowable）通过 → 出库；驳回 → 回滚：Lua 恢复库存 + 冲正流水
  ⑥ 超时自动关单：RocketMQ 延迟消息（30 分钟）→ 未审完则 已关闭 + 回滚 + 冲正
  ⑦ 对账兜底：XXL-Job 定时比对 Redis 预扣 vs DB 流水 → 差异告警（站内信）+ 修复
```

- **幂等**：消费者以 `req_no` 唯一索引 + 消费状态表（或状态机判断）防重复投递；接口层防重复提交（基座幂等组件 + 前端防抖）；
- **防超卖三道防线**：Lua 原子预扣（前端）→ DB 乐观锁约束（`available >= qty` 条件更新，最后防线）→ 对账 Job（事后）；
- 压测断言：并发结束后 `期初库存 == available + sum(成功流水扣减)` 且 Redis 与 DB 一致 → **0 超卖**；
- V1/V2 用配置开关切换（同一接口两实现），保证压测可比、面试可讲对照。

### 6.2 缓存体系

| Key | 内容 | 策略 |
| --- | --- | --- |
| `pm:stock:{projectId}:{materialId}` | 可用库存（预扣） | Lua 原子操作；变更走 MQ 异步落库 |
| `pm:material:{id}` / 目录树 | 物料/目录 | Caffeine(一级) + Redis(二级)；TTL+随机防雪崩；逻辑过期+Redisson 锁重建防击穿 |
| `bf:material` | 物料 id 集合 | Redisson 布隆过滤器，防穿透；误判率 1%；新增物料异步 rebuild |
| `pm:catalog:all` 空值 | 不存在 key | 空值缓存短 TTL（60s）兜底 |

- 双写一致性：先更新 DB → 删除缓存（+延迟双删）；Canal 订阅 binlog 作为扩展方向（不在一期实现，面试可讲思路）。

### 6.3 分库分表（ShardingSphere-JDBC）

- 对象：`bc_stock_log`（增长最快的流水表，压测会灌百万级数据）；
- 策略：按 `project_id` 哈希 → **逻辑 4 库 × 每库 8 表 = 32 分片**；受 16G 本机资源约束（D18），4 个逻辑库以**单机 MySQL 实例多 schema 模拟**（`pm_log_0..3`），分片路由与跨库归并逻辑与真实多库一致；
- 分片键理由（面试必答）：业务查询天然带 project_id（数据权限 + 流水查询），避免跨片路由；全局查询走异步聚合（分片并行查 + 归并）或限制必须带项目条件——在文档中明确取舍；
- 全局 ID：雪花算法（MyBatis Plus ASSIGN_ID），讲清"为什么分片后不能用自增"；
- 迁移方案（面试点，写进文档）：双写 → 存量迁移脚本（按 project_id 重分布）→ 数据校验对账 → 切读 → 停旧写，附回滚预案。

### 6.4 分布式事务（Seata AT）

- 场景：审批通过回调链路——`buildcloud-material` 出库扣减 + `buildcloud-project` 项目成本归集更新（跨服务）；
- 集成 Seata AT，演示 undo_log 与回滚；同时保留本地消息表 + 对账 Job 作为最终一致性兜底（面试讲两者取舍：AT 强一致但有短暂全局锁，异步链路用事务消息更合适）。

### 6.5 异步报表（见 §5.4）

讲点：大数据量不分页深翻页问题 → 分片任务 + 流式写 + OSS + 通知的完整异步化方案；EasyExcel 避免内存溢出（对比 POI）。

### 6.6 AI / RAG（见 §5.5）

讲点：为什么 RAG 而非微调；chunk 大小/重叠调参；混合检索与 rerank；SSE 长连接与网关兼容；会话记忆裁剪；引用溯源防幻觉；**多供应商动态切换与成本治理（D19）**。
