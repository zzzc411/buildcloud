## 1. 高并发申领（占位）

> 状态：占位骨架，随 W5 专项产出（plan-w5-concurrent-v2）填充为初稿。本章数字一律待压测报告（W8）。

**弹药来源**：plan-w4（V1 基线实现）、plan-w5（V2 目标架构与压测）、spec §2.3（压测场景边界）、§5.2（材料域设计）、§6.1（V1→V2 对照）。

**预设问题**：

1. 集中申领为什么是高并发场景？热点瓶颈具体在哪？
   - 要点指引：场景设定为月底/开工高峰，多个工地同时申领同一物料，瞬时高并发打向同一库存记录；热点是同一库存行的数据库行锁（spec §2.3）。
2. V1 同步扣减是怎么做的，为什么扛不住？
   - 要点指引：同一事务内 `SELECT ... FOR UPDATE` 锁库存行 → 校验扣减 → 写单与流水；行锁串行化导致热点记录成为瓶颈；明确 V1 是压测对照组而非保留方案（spec §6.1）。
3. V2 目标架构的完整链路？
   - 要点指引：Sentinel 限流（接口级 + 热点参数 materialId）→ 布隆过滤器 + 两级缓存快速校验 → Redis Lua 原子预扣 → RocketMQ 事务消息 + 本地事务 → 消费端 DB 乐观锁扣减 → 审批出库/驳回回滚 → 延迟消息超时关单 → 对账 Job 兜底（spec §6.1 流程 ①–⑦）。
4. 防超卖有几道防线，各自兜什么？
   - 要点指引：三道防线——Lua 原子预扣（第一道）→ DB 乐观锁条件更新 `available >= qty`（最后防线）→ 对账 Job（事后修复）；压测断言口径：期初库存 == 可用库存 + 成功流水扣减之和，且 Redis 与 DB 一致；**实测数字以压测报告为准**。
5. 为什么用 Lua 脚本做预扣，而不是直接 GET/SET？
   - 要点指引：「判断余量 + 扣减 + 记录预扣明细」必须是原子操作，拆开执行在并发下存在检查-扣减竞态（spec §6.1 ③）。

## 2. 缓存体系（占位）

> 状态：占位骨架，随 W5 专项产出填充为初稿。

**弹药来源**：plan-w5、spec §6.2。

**预设问题**：

1. 哪些数据进了缓存，各自的 key 与策略是什么？
   - 要点指引：库存预扣（Lua 原子操作，变更走 MQ 异步落库）、物料/目录（Caffeine + Redis 两级）、布隆过滤器（防穿透，误判率 1%，新增物料异步 rebuild）、不存在 key 的空值短 TTL 兜底（spec §6.2 表格）。
2. 为什么做 Caffeine + Redis 两级？一级缓存的一致性代价是什么？
   - 要点指引：物料目录读多改少，本地缓存省网络往返；代价是各节点本地副本失效时机不一致，需要明确失效策略（随 W5 设计文档填充）。
3. 缓存穿透/击穿/雪崩分别怎么防？
   - 要点指引：穿透——布隆过滤器 + 空值缓存短 TTL；击穿——逻辑过期 + Redisson 分布式锁重建；雪崩——TTL 加随机（spec §6.2）。
4. 缓存与 DB 双写一致性怎么处理？
   - 要点指引：先更新 DB → 删除缓存（+延迟双删）；Canal 订阅 binlog 作为扩展方向（一期不实现，面试讲思路与取舍）（spec §6.2）。
5. 库存数据为什么不能「只放缓存」？
   - 要点指引：Redis 是预扣视图，DB 是最终事实，两者经 MQ 异步落库 + 对账 Job 收敛——衔接第 3 章。

## 3. MQ 与一致性（占位）

> 状态：占位骨架，随 W5/W6 专项产出填充为初稿。

**弹药来源**：plan-w5、plan-w6、spec §6.1（④⑥）、§6.4。

**预设问题**：

1. 为什么选 RocketMQ，而不是 Kafka / RabbitMQ？
   - 要点指引：基座微服务版默认（如实说选型约束）；且本项目需要事务消息与延迟消息两个特性，RocketMQ 原生支持（spec §3.3、§6.1）。
2. 事务消息怎么保证「预扣成功 → DB 必然落库」？
   - 要点指引：half 消息 → 本地事务（创建申领单 + pending 扣减流水）→ commit 后消费者扣减 DB；本地事务失败则 rollback，MQ 丢弃 half 消息，预扣由对账回滚（spec §6.1 ④）。
3. 消费端怎么幂等？
   - 要点指引：`req_no` 唯一索引 + 消费状态表（或状态机判断）防重复投递；接口层用基座幂等组件 + 前端防抖（spec §6.1 幂等节）。
4. 延迟消息用在哪？
   - 要点指引：申领单超时自动关单（延迟消息）→ 未审完则关单 + 回滚预扣 + 冲正流水（spec §6.1 ⑥、§5.2 状态机）。
5. 消息丢了或反复消费失败怎么办？
   - 要点指引：重试与死信告警；对账 Job 定时比对 Redis 预扣与 DB 流水，差异告警（站内信）+ 修复——最终一致性的兜底闭环（spec §6.1 ⑦）。

## 4. 分库分表（占位）

> 状态：占位骨架，随 W6 专项产出填充为初稿。

**弹药来源**：plan-w6、spec §6.3、D18。

**预设问题**：

1. 为什么要分？为什么选 `bc_stock_log`？
   - 要点指引：库存流水是增长最快的表，压测将灌入大规模流水数据，是分库分表的唯一对象（spec §6.3）。
2. 分片键为什么是 `project_id`？不带项目条件的查询怎么办？
   - 要点指引：业务查询天然带 project_id（数据权限 + 流水查询），避免跨片路由；全局查询走异步聚合（分片并行查 + 归并）或限制必须带项目条件——取舍在文档中明确（spec §6.3）。
3. 为什么是逻辑 4 库 × 8 表、单机多 schema 模拟？
   - 要点指引：受 16G 本机资源约束（D18），4 个逻辑库以单机 MySQL 多 schema 模拟，分片路由与跨库归并逻辑与真实多库一致；向面试官如实说明模拟口径与等价性（spec §6.3）。
4. 分片后主键怎么生成？
   - 要点指引：雪花算法（MyBatis Plus ASSIGN_ID）；讲清为什么自增 ID 分片后会冲突（spec §6.3）。
5. 存量数据怎么迁移上线？
   - 要点指引：双写 → 存量迁移脚本（按 project_id 重分布）→ 数据校验对账 → 切读 → 停旧写，附回滚预案（spec §6.3）。

## 5. 分布式事务（占位）

> 状态：占位骨架，随 W6 专项产出填充为初稿。

**弹药来源**：plan-w6、spec §6.4。

**预设问题**：

1. 项目里哪些点真的需要分布式事务？
   - 要点指引：审批通过回调链路——`buildcloud-material` 出库扣减 + `buildcloud-project` 项目成本归集更新，跨服务写（spec §6.4）。
2. 为什么用 Seata AT？和「全用消息最终一致」怎么取舍？
   - 要点指引：AT 强一致但有全局锁开销，适合同步链路；异步链路用事务消息更合适——两者并存各管一段，面试讲取舍逻辑（spec §6.4）。
3. AT 模式两阶段的原理？`undo_log` 干什么用？
   - 要点指引：一阶段记录前后快照并提交本地事务，二阶段按全局决议提交或用快照回滚；以集成演示与 W6 设计文档为准填充。
4. 本地消息表 + 对账 Job 兜底怎么设计？
   - 要点指引：保留为最终一致性兜底；与事务消息方案的差异与适用场景对照（spec §6.4）。
5. 事务边界怎么划分？
   - 要点指引：单库事务 / Seata AT / 事务消息三类各自适用场景的判断标准（强一致要求、同步/异步、锁冲突面）——随 W6 设计文档定稿。

## 8. 二次开发叙事

> 状态：**Phase 1 完整成文**，可独立脱稿使用。口径与 spec v1.1 §1.2 完全一致：**基于开源微服务基座做二次开发，通用能力（用户/权限/工作流引擎）来自基座，六个业务域、高并发链路、AI 模块、部署上线为自己设计与实现**。不夸大自研范围，被问基座来源时大方承认——与真实公司里基于内部平台二次开发的工作模式一致。
> 本章按叙事与流程层面作答，不涉及性能数字（数字纪律见文首 R-6 条目）。

### 8.1 一句话口径

> 「我第一段实习在建筑公司技术部门全栈维护一个工程项目管理平台；后来业余时间基于开源微服务基座做二次开发，把这套业务按微服务架构重新实现了一遍——通用能力（用户/权限/工作流）来自基座，六个业务域、高并发材料申领链路、RAG 制度知识库和云服务器部署上线，是我自己设计与实现的。」

### 8.2 完整展开叙事（自我介绍底稿）

**【实习背景】** 第一段实习在建筑公司技术部门，全栈维护公司内部使用的工程项目管理平台，业务覆盖项目立项、合同资金、材料库存、多级审批这些环节；既写业务代码也参与部署运维，对这套业务的完整链路和实际使用痛点比较熟。

**【发现痛点】** 实习期间观察到，单体架构在两个场景有明显瓶颈：一是**材料集中申领**——月底/开工高峰期多个工地同时申领同一种物料，热点库存记录把响应拖垮；二是**大报表导出**——大数据量查询把应用和数据库同时拖住。当时只能用最朴素的方式缓解，没有条件做架构级改造，这是我决定业余时间重做这套系统的直接动因。

**【决定与做法】** 于是按微服务架构把这套业务重新实现一遍。通用能力——系统管理、用户/租户/权限、工作流引擎、文件这些每套系统都一样的部分——直接采用开源企业级微服务基座：芋道 yudao-cloud 的 master-jdk17 分支（JDK 17 + Spring Boot 3.5），并做了裁剪：删掉 15 个与建筑业务无关的模块（商城/支付/CRM 等），保留网关与三个基座服务；自己新增 4 个业务服务：项目合同、材料、报表、AI。这个选择后面细讲（见 8.4 追问层 2）。

**【技术主线】** 把实习里见到的瓶颈当作主线来做深：

- **高并发申领**：做了 V1（同步扣减）到 V2（Redis Lua 原子预扣 + RocketMQ 事务消息异步落库 + 幂等消费 + 对账兜底）的对照演进，配套 Sentinel 限流、两级缓存、防超卖三道防线，并出具压测报告验证（**数字一律按压测报告口径引用，本底稿不预填数字**）；
- **一致性与数据量**：申领流水做分库分表（ShardingSphere-JDBC，按 project_id 分片），审批跨服务链路用 Seata AT + 本地消息表兜底；
- **AI**：结合对 AI 应用开发的兴趣，实现了 RAG 制度知识库问答——文档解析分块、向量+关键词混合检索、SSE 流式输出、引用溯源防幻觉、多供应商动态配置与故障切换；
- **报表**：大数据量异步导出（XXL-Job 分片任务 + EasyExcel 流式写 + 文件服务 + 站内信通知）。

**【收尾】** 最终完成云服务器部署上线并对外演示，全流程可跑通：立项 → 合同 → 申领 → 审批 → 出库 → 报表 → AI 问答。每个技术点我都能讲清决策依据、替代方案的取舍和出问题后的预案——这也是我准备面试的方式（见本弹药库的三层追问结构）。

> 使用提示：本底稿按项目**最终交付状态**撰写（排期至 W8 定稿）。阶段性使用时按实际进度如实调整表述——例如压测报告尚未定稿时，说「压测报告在整理中」；某专项未完成时，如实说明当前进展，不提前声索。

### 8.3 高频追问：「是不是芋道改的？」

**应对原则**：大方承认基座来源（spec §1.2 红线原文），随即划清贡献边界，最后拉平到真实工作模式。三步话术：

1. **第一步：直接承认，给出事实。**
   > 「对，基座是芋道 yudao-cloud（master-jdk17 分支，JDK 17 + Spring Boot 3.5）。仓库是公开的，README 里注明了基座来源和 MIT 协议，这一点我没有回避。」
2. **第二步：划清贡献边界**（不贬低基座，也不把基座能力说成自己的）。
   > 「基座承担的是通用能力：网关、用户/租户/RBAC 权限、字典、Flowable 工作流引擎、文件这些。我在它之上做了两类工作：一是**裁剪**——删掉 15 个与建筑业务无关的模块，清理 pom、Nacos 配置、SQL、网关路由、菜单和前端的连带改动，并保留来源与协议声明；二是**自研**——新增 4 个服务（项目合同/材料/报表/AI），业务表设计与状态机、高并发申领链路（Redis Lua 预扣 + RocketMQ 事务消息 + 幂等 + 对账）、分库分表、Seata 事务场景、RAG 全链路，都是我做的，设计文档和单测都在仓库里。」
3. **第三步：拉平视角**（给面试官定调）。
   > 「这和公司里基于内部平台/中台做业务二次开发的模式是一样的——关键是清楚哪部分是复用、哪部分是自研，以及自研部分为什么这么设计。您想深入哪一块，我可以展开讲。」

**应对禁忌**：

- **不否认**——仓库公开可查，否认基座来源等于直接出局；
- **不抢功**——把基座能力说成自己写的，追问两句就穿帮；
- **不自贬**——只说「就是个开源项目改的」，等于放弃自研部分的含金量；贡献边界用事实说话。

### 8.4 三层追问预演（叙事与流程层面）

#### 追问层 1：为什么这么做——为什么基于开源基座二次开发，而不是全部自己写？

- **价值导向**：我想深挖的是高并发链路、一致性、AI 应用、部署上线这些有区分度的部分；用户/权限/工作流是所有系统都一样的成熟轮子，重写它们不产生学习增量，反而会把有限周期消耗在低价值的重复工作上。
- **真实工作模式**：企业开发本来就是在内部平台之上做业务。能读懂一个成熟基座的工程规范（分层结构、错误码段位、统一响应、单测风格），并让自研模块完全按它的规矩写（包名 `com.buildcloud.*` 与基座 `cn.iocoder.yudao.*` 隔离、错误码独立段位、BaseDO 六字段对齐），本身就是工程化能力的体现。

#### 追问层 2：替代方案与取舍——有没有考虑过其他路线？

| 方案 | 做法 | 取舍 | 结论 |
| --- | --- | --- | --- |
| 纯自研 | 从零搭微服务框架 + 自己实现权限/工作流/文件 | 学习价值集中在基建侧，但周期内六域业务 + 高并发 + AI + 部署会全部变浅 | 否 |
| 官方精简版 | yudao-cloud-mini（只含 system+infra），按官方迁移文档把 bpm 迁入 | 起点干净，但 bpm 迁移本身是额外风险项 | 备选路线（完整版裁剪踩坑再切换） |
| 完整版裁剪（采用） | 新建仓库拷贝完整 yudao-cloud，删除 15 个业务无关模块 | bpm 与参考代码在手边；代价是清理连带改动（pom / Nacos / SQL / 网关路由 / 菜单 / 前端）并保留来源与 MIT 协议声明 | **采用**（spec D1/D2） |

配套两条原则：

- **基座代码原则上只读**——确需修改先记 ADR 说明理由与影响面（项目红线 R-2），保持「我的改动」可审计；
- **AI 域自研**——不继承基座自带 AI 模块（不参与构建，仅作设计参考），RAG 全链路用自研 `buildcloud-module-ai` 实现，如实向面试官说明「参考过其设计」这一层（spec §4.2、D12）。

#### 追问层 3：线上出问题怎么办——基座部分和自研部分怎么分责？（流程层面）

- **基座部分**：先查上游社区（issue / 文档 / 更新日志）确认是否已知问题；能用配置或降级规避的先规避，不动基座源码；确需修改时按项目约束先记 ADR，并在基座版本升级时重新评估该改动（上游修复后优先回归上游方案）。
- **自研部分**：自己兜底——核心链路（预扣 / 消费 / 回滚 / 对账）有单测与预案；出问题先限流止血，再通过对账 Job 修复数据，最后复盘补测试。各专项的具体监控与回滚预案在第 1–7 章展开（随专项产出填充）。
- **隔离原则**：自研模块与基座模块通过独立包名（`com.buildcloud.*` / `cn.iocoder.yudao.*`）和独立错误码段位隔离，故障排查时归属边界清晰；这也是「线上出问题怎么办」在架构层面的第一道答案。

### 8.5 诚信自查清单（开口前过一遍）

1. 通用能力（用户/租户/RBAC/字典/工作流/文件/网关）→ 归**基座**，绝不表述为自研；
2. 六域业务（表设计/状态机/用例）、高并发申领链路、分库分表、Seata 事务场景、RAG 全链路、部署上线 → 归**自研**，可展开讲；
3. 基座来源（yudao-cloud master-jdk17）→ README 主动注明，被问大方承认；
4. 性能数字 → 只引用 `docs/testing/` 压测报告数字；报告未出的字段一律回答「以压测报告为准」，不估算、不引用目标值冒充实测值；
5. AI 模块 → 自研实现；如被追问与基座 AI 模块的关系，如实说明「其源码保留作设计参考，未参与构建」。
